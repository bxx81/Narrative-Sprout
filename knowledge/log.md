## 2026-10-15
* **Fix**: The Game screen's scene image now starts loading during the route transition, like the card images. `ImageDisplay`'s blob bookkeeping and load effects were plain `useEffect`, which React defers until the view transition finishes, so the `/play` entry (title Continue / Starting → play / History resume) only began `createObjectURL` + decode after the cross-fade. All four effects are `useLayoutEffect` now. Measured on real Edge while entering `/play`: the call lands inside the `:active-view-transition` window (~0.8 s; the run's transition was 781–1126 ms) with the fix, versus a call recorded after the window with the former code. Documented in [Route Transitions](/features/route-transitions.md) (deferral rule).
* **Change**: The document scrollbar is now an overlay scrollbar (`overlayscrollbars` 2.16, own vendor chunk via `manualChunks`). `initializeDocumentScrollbar()` (`src/features/scrollbar/`, registers `ClickScrollPlugin` for `clickScroll`) runs from `App` with `autoHide: "leave"` + `autoHideSuspend: true`, `dragScroll` and `clickScroll`; theming via design tokens in `src/styles/overlayScrollbar.css` (`theme: null`). The native scrollbar never takes layout space anymore, so View Transition captures always share one width: this replaces `html { scrollbar-gutter: stable }` (removed) and the title screen's edge-sampling gradient (removed). Reason found by measurement on Edge 155: the classic-scrollbar lane can only be painted by the canvas background **color** — background images (body/html, `cover`/`100vw`/`fixed`), fixed elements and box-shadows are all clipped at the lane edge — and the old `innerWidth - clientWidth` detection never fired on the non-overflowing title where the lane was exposed. The macOS-style problem (native overlay bars appear only on scroll, so they cannot be clicked until a wheel scroll reveals them) is also gone: the bar shows while the pointer is inside the window. `index.html` carries `data-overlayscrollbars-initialize` on `html`/`body` for a flicker-free start; body initialization keeps `document.scrollingElement = html`, so `window.scrollY`/`scrollTo` and the AppLayout pin/release machinery are unchanged; `cancel` defaults are kept (mobile cancellation falls back to the native bar) and the bar is hidden while `:active-view-transition` matches. Verified on real Edge against the running app: no lane on the title (`html` width == `innerWidth`), hover-visible bar on overflowing screens, `window.scrollTo`, drag and track-click, `display: none` during a title → settings cross-fade. New page [Overlay Scrollbar](/features/overlay-scrollbar.md); [Route Transitions](/features/route-transitions.md) and [Key Dependencies](/references/key-dependencies.md) updated.
* **Addition**: Route changes now cross-fade through React's `<ViewTransition>` (React upgraded 19.0 → 19.3 for the stable API), and the zoom overlay scales in on open. The boundaries are **Chromium-gated** (`src/features/viewTransition/api.ts`): Playwright's WebKit hard-crashes the renderer on `document.startViewTransition()` when the document is exactly one viewport tall (reproduced in dev and prod; routine via `min-h-screen` screens with short content; bisected to real content + exact height — trivial/scrollable/shorter pages pass), and WebKit's implementation has a use-after-free crash history reaching React itself (GH-35336, enter/exit on iOS Safari) and the Tauri targets (WebKitGTK; the reported workaround is disabling view transitions). Non-Chromium engines keep the CSS fallbacks (pathname-keyed mount fade; `isClosing` zoom fade); only Chromium family (Chrome/Edge/Tauri WebView2) animates. The boundary names a viewport-tall wrapper inside it, so fixed full-bleed decorations (the title background) are not clipped to a shorter screen box in the snapshot. New page [Route Transitions](/features/route-transitions.md); Routing row in `overview/project-overview.md`, React version in `references/key-dependencies.md`, and Key Design Decisions in `overview/architecture.md` updated.
* **Fix**: The cross-fade no longer flashes the outgoing screen at the end — the `::view-transition-old/new` fades need an explicit `both` fill mode, or the old snapshot reverts to opacity 1 when its animation ends (Chromium runs a parallel UA root cross-fade at 250 ms beside the boundary's 300 ms pair). `e2e/viewTransitions.spec.ts` asserts the running animation's fill mode so the flash cannot regress silently.
* **Addition**: Keeping the outgoing screen still took the scroll/scrollbar machinery in `AppLayout` — the outgoing snapshot is anchored to the document, so (a) a passive scroll listener pins `min-height = scrollY + innerHeight` on the route wrapper (protects the font-wait gap, where the browser otherwise clamps the scroll the moment a shorter incoming screen commits, dragging the old snapshot), (b) a `useLayoutEffect` inside the update callback pins the wrapper height to the outgoing height (the group animation maps the snapshots through the old/new size difference and drifts the outgoing content at fractional device pixel ratios), pushes the incoming screen down by `scrollY` plus its own top padding via `padding-top` (its snapshot captures its own top; removal is shift-free) and sets `html { overflow-y: hidden }` (the pins make the document artificially scrollable, so the scrollbar would otherwise paint a stale position mid-fade), and (c) a deferred release effect — waits for `:active-view-transition` to stop matching, because the mid-transition setStates from image loading flush effects early — removes the pins, resets the scroll and restores the scrollbar in one frame (in that order). `html { scrollbar-gutter: stable }` reserves the classic-scrollbar lane so both captures keep the same width (overlay platforms reserve nothing); the title screen paints the lane with a four-stop gradient sampled from its photo's right edge at the layer's 0.6 brightness (`try/catch` for tainted Tauri asset canvases). Edge's "always show scrollbars" toggle shows a real bar in the lane; with auto-hide the lane blends into the photo.
* **Fix**: Card images and zoom-overlay input no longer wait out the animation — React defers `useEffect` until a view transition finishes, so `useLazyNodeImage` now observes/loads in `useLayoutEffect` (measured: the blob URL lands ~9 ms after mount, previously ~25 ms after the animation ended) and `ZoomOverlay`'s key/focus effects are layout effects (Escape works while the overlay animates in).
* **Testing**: New `e2e/viewTransitions.spec.ts` (boundary activation on Chromium via live `::view-transition` pseudo-element animations incl. the fill mode; the DOM path on both engines). Counts corrected in `operations/testing.md` (68 unit files / 365 tests; 8 e2e specs / 46 tests). Technique worth remembering: pause the view-transition animations the moment they appear and seek `currentTime` for stable mid-transition frames — plain 60 ms screenshot sampling repeatedly misled. Playwright's Chromium here uses overlay/hidden scrollbars, so classic-scrollbar behavior (the lane) is only verifiable on a real browser.
* **Fix**: `longpress.spec.ts` flake (raw mouse/touch down landing mid route cross-fade never started the app's long-press timer). Root cause found by probe: **Chromium blocks pointer input while a view transition animates** — hit-testing lands on the `::view-transition` overlay and retargets to `<html>` (an explicit `::view-transition { pointer-events: none }` does not change it, tried and reverted). `e2e/helpers/story.ts` gained `waitForRouteTransition` (waits for `:active-view-transition` to appear, bounded, then clear; Chromium-gated) and `startStory` now ends with it; the long-press holds await the copy toast instead of a fixed 1300 ms so a CPU-delayed timer cannot turn a completed gesture into a cancelled one. Documented in [Route Transitions](/features/route-transitions.md) (verification section).

## 2026-10-11
* **Change**: Release assets are hands-off. New `.github/workflows/tauri-release.yml` runs on the GitHub Release release-please publishes (`release: types: [published]`; `windows-latest`; `oven-sh/setup-bun@v2` + `dtolnay/rust-toolchain@stable` + `Swatinem/rust-cache@v2` `workspaces: src-tauri`) and builds through `tauri-apps/tauri-action@v1` with `tauriScript: bun run tauri` — the identical `bun run tauri build` a local release build runs (the `tauri` script runs `sync:tauri-version` first) — uploading the NSIS setup (`src-tauri/target/release/bundle/nsis/Narrative Sprout_<version>_x64-setup.exe`) onto that release via `releaseId`; `uploadUpdaterJson: false` because the app has no updater. `github.event.release.tag_name` is the checkout ref, so the moving release-please tag format (2.0.1 shipped as `narrative-sprout-v2.0.1`, 2.0.0 as `v2.0.0`) does not matter.
* **Fix**: `Cargo.lock` no longer needs a manual refresh after every release-PR merge. Verified against the project's cargo 1.99: cargo rewrites `Cargo.lock` on every invocation and strips comments — a `# x-release-please-version` annotation on the `narrative-sprout` version line disappears on the next `cargo` run **even when the lock already matches the manifest** — so the lock cannot be a release-please extra-file. Instead, the release workflow's last step commits the build's own cargo-refreshed `Cargo.lock` back to `main` (`chore: refresh Cargo.lock for <tag>`), skipped when `main` is strictly ahead of the release commit so dependencies merged in the meantime can never roll back. Net effect: after each release, `main` is cargo-canonical again and no local build dirties the tree; only the window between the release-PR merge and the release workflow's back-commit still shows the one-line refresh.
* **Change**: The release workflow carries the desktop Google Drive OAuth values. Documented in `operations/build-and-deploy.md` (Release Assets) and README.

## 2026-09-27
* **Fix**: Long-press copy on a choice button can no longer swallow the next ordinary click. `GameChoices.tsx` moved from `mouse*`/`touch*` handlers to a Pointer Events state machine: `pointerdown` (primary button only) records the pointer id + press origin and **clears** `suppressNextClickRef` (renamed `longPressTriggered`), a wander past the new `LongPressMoveSlopPx` (10 px) or `pointerup`/`pointercancel`/`pointerleave` ends the press, and the timer callback sets the latch so the trailing `click` is swallowed exactly once in `onClick`. The old latch lived only inside `onClick`, so a long press that ended without a `click` reaching the button — mouse released off the button (the click lands on the common ancestor, `MAIN`), or a finger that drifted before lift-off (the browser drops the synthesized mouse/click events entirely) — left it set and ate one later click. An unmount cleanup clears the pending timer; the overwrite-at-`pointerdown` reset doubles as self-healing for a pointer id that never saw its `pointerup`. Accepted edge: keyboard Enter immediately after a long press loses one submission.
* **Addition**: Copy-to-form is announced — new i18n key `toastChoiceCopied` in all 5 locales (279 → 280 keys each) plus `toast.success(...)` in the `GameChoices` long-press timer and in `GameScreen`'s choice-echo timers, which now share the extracted `applyChoiceEchoPreset()` (1000 ms mouse / 500 ms touch). The `choicePreset` apply effect in `GameChoices` deliberately stays silent, otherwise one gesture would toast twice; `ToastSoundPlayer` plays `notification.ogg` for the new toast as it does for every other. Documented in `features/game-loop.md` (new Long-press copy bullet).
* **Testing**: New `e2e/longpress.spec.ts` (5 cases: mouse release-on-button, mouse release-off-button, choice echo, touch long press, touch + finger drift) and the shared `e2e/helpers/story.ts` `startStory()` helper (also migrated `playthrough.spec.ts` off its inline flow). Both touch cases hold the pointer through CDP `Input.dispatchTouchEvent` because Playwright's `tap({ delay })` awaits the delay *before* the tap (its Chromium delegate sends `touchStart`/`touchEnd` back to back), so they are chromium-only — WebKit keeps the three mouse cases.
